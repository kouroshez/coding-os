# TASK-075: Graph — process-grouped search

**Outcome (one sentence):** `cos_graph_query` returns `processes[]` with `{summary, priority, step_count, members[]}` keyed by community, and the Search tab renders grouped results (e.g. `authentication middleware` clusters into `LoginFlow` / `RegistrationFlow` / `TokenRefresh` buckets with step-ordered nodes) — the differentiator layer that lets coding-os beat graph-tool by leveraging formula dispatch + cognition traces.

## Acceptance (G/W/T) — *this IS the Definition of Done*

- **Given** a repo with recognisable flows (login, registration, token refresh)
  **When** the Leiden pass runs (`cos graph-communities` or automatic post-reindex)
  **Then** `COMMUNITY` nodes exist with `name`, `priority` (size × centrality), `summary` (LLM-light: top 3 functions joined), and `MEMBER_OF` edges from each member to the community.
- **Given** `cos_graph_query("authentication middleware")` via MCP
  **When** the tool returns
  **Then** response contains `processes: [{id, name, summary, priority, step_count, members: [{node_id, step_index}]}]` sorted by priority, alongside the flat `matches[]` we already return.
- **Given** the Search tab with a similar query
  **When** results render
  **Then** each process appears as a collapsible group header showing name + summary + priority badge, and members render in step-index order inside the group. The flat-matches section appears below under "Other matches".
- **Given** a query with no clear clustering signal
  **When** results return
  **Then** `processes[]` is empty and the UI falls back to the flat list seamlessly — no empty group headers.
- **Tests:** `core/graph_os/tests/test_process_grouping.py` with a 3-cluster golden fixture; `e2e/search-processes.spec.ts` asserts group rendering, collapse, and step ordering.

## Implementation Notes

1. **Community detection:** use `networkx.community.louvain_communities` (simpler and license-compatible) or port the Leiden pass hinted at by TASK-040. Run post-reindex; persist community nodes as part of the graph SSOT.
2. **Priority formula:** `priority = log10(member_count + 1) × avg(entry_score of members)` — uses TASK-081's entry-point score.
3. **Process naming:** pick the highest-entry-score member as the anchor and use its function name + a 1-line summary generated by joining top-3 member names — no LLM required for v1. Add optional LLM summary behind a feature flag (hooks into TASK-079's LLM pipeline).
4. **Step ordering:** DFS from the community's highest entry-score anchor, record visit order; tie-break by source file path.
5. **Query integration:** `cos_graph_query` fans out — runs the existing hybrid search, then groups hits by their `MEMBER_OF` target (if any), preserving hits with no community as "flat matches".
6. **UI:** add a `<ProcessGroup>` component to `UnifiedSearch.tsx`; each group is a `<details>` element, default-expanded when member count ≤ 5.

## Differentiator angle

coding-os has F1–F11 formula dispatch + cognition traces. Processes can (in a follow-up task) be annotated with "which formula touches which step", turning the Search tab into an agent-activity map graph-tool cannot produce.
